#risk #ers
## 1. The Two Indexes: Distinct Roles

### 📊 Index `risk` — the **raw journal** of risk events
- **Content**: every individual **risk modifier** generated by a correlation search with a `Risk Analysis` response action.
- **Granularity**: one event = one point-in-time risk contribution.
- **Key fields**: `risk_object`, `risk_object_type`, `risk_score`, `risk_message`, `source` (correlation search name), `annotations.mitre_attack.*`, `threat_object`.
- **Retention**: typically long (90–365 days) to support historical analysis and hunting.

Typical event:
```splunk-spl
_time=...  risk_object=srv-sap-01  risk_object_type=system  
risk_score=20  source="ESCU - Linux Auditd Add User Account"  
annotations.mitre_attack.mitre_tactic=persistence
```

👉 **Atomic source of truth**: _"at this moment, this object gained X points for this reason."_

---
### 🎯 Index `ers` (Enterprise Security Risk Scoring / _Risk Notables_) — the **RBA aggregates**
Since ES 7.x and consolidated in ES 8, `ers` stores:
- **Risk Notables** created by the RBA framework when a threshold is breached (e.g. `risk_score > 100` over 24h + `≥3 MITRE tactics`).
- **Consolidated events**, pre-aggregated by `risk_object` over a time window.
- Used by ES **Risk Analysis dashboards** for fast rendering.

**Key fields**: `risk_object`, `risk_score` (aggregated, frozen at notable creation), `source` (name of the Risk Incident Rule, **not** the detection), `mitre_tactic_count`, `contributing_sources`, `contributing_events`.

👉 **"Notable" view**: _"this object crossed a threshold — here is the consolidated SOC alert."_

## 2. Why `ers` ≠ an Asset's Risk Score

|Reason|Impact|
|---|---|
|**Different time windows**|Risk Analysis UI uses a sliding window on the `Risk` datamodel; `ers` only holds notables already triggered.|
|**`ers` is a derived product**|The true risk sum is always computed from `index=risk`.|
|**Decay not reflected**|Decay logic (e.g. −50% after 7d) is applied at search time, not stored in `ers`.|
|**Different scope**|`ers` misses everything below the RBA threshold (critical for hunting).|
|**Secondary objects in notables**|A notable on a user may mention related systems → asset appears in `ers` without having accumulated score itself.|

### Scope comparison

|Aspect|`index=risk`|`index=ers`|
|---|---|---|
|All risk modifiers|✅|❌|
|Only those above RBA threshold|❌|✅|
|Real-time scoring usable|✅|❌|
|Source for Risk Analysis dashboards|✅ (primary)|Partial|

## 4. Best Practices

### ✅ Compute the **true risk score** of an asset

```splunk-spl
| tstats summariesonly=true 
    sum(All_Risk.calculated_risk_score) as risk_score 
    dc(All_Risk.annotations.mitre_attack.mitre_tactic) as mitre_tactics 
    dc(All_Risk.source) as nb_detections 
  FROM datamodel=Risk.All_Risk 
  WHERE All_Risk.risk_object_type=system earliest=-7d 
  BY All_Risk.risk_object
| sort - risk_score
```

### ✅ List active **RBA notables**

```splunk-spl
index=ers earliest=-24h 
| stats values(source) as rules 
        values(annotations.mitre_attack.mitre_tactic) as tactics 
        sum(risk_score) as score 
  by risk_object
```

### ⚠️ Avoid
- Using `index=ers` as the "current score" reference → you miss all sub-threshold context, which is essential for hunting.
- Confusing `risk_score` (per-event value) with `calculated_risk_score` (accumulated value from the datamodel).

## 5. ES 8 Specifics

- **Mission Control** is now the central incident UI.
- Consolidation around the **`Risk` datamodel** rather than direct index searches.
- **Risk Factors** are configurable multipliers based on asset `priority` / `category` → a well-populated **Assets & Identities** lookup directly impacts `calculated_risk_score`.

→ Enriching the `priority` field on your assets **directly drives** the final score and the urgency color shown in Mission Control.
