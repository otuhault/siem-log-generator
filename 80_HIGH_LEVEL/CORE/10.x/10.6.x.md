# Splunk Enterprise 10.6.x

> [!summary] Executive Summary
> **Splunk Enterprise 10.6.4** introduces key architectural alignments between *On-Premises* deployments and *Splunk Cloud*. Major highlights include the rollout of the unified 4-segment versioning scheme, supported Data Management Service REST APIs for Edge and Ingest Processor automation, on-premises configuration change tracking, and runtime app management optimizations reducing service restarts by up to 50%.

---
### 1. 🏷️ Unified 4-Segment Versioning Scheme
> [!info] Standardized Versioning Structure
> Starting with the 10.6 release train, Splunk standardizes release numbering as **`Major.Minor.Maintenance.Patch`**:
> * **10** : Major version (Core engine changes and fundamental architectural milestones).
> * **6** : Minor version (New platform features, capabilities, and public APIs).
> * **4** : Maintenance release (Consolidated stability fixes and operational enhancements).
> * **x** : Critical security patch or hotfix (e.g., `10.6.4.1`).

---
### 2. ⚡ Core Capabilities & Operational Enhancements

#### A. Data Management Service APIs (Edge & Ingest Processors)
* **Platform Engineering Automation:** Exposes official, supported REST APIs to programmatically manage, deploy, and monitor Edge Processor and Ingest Processor pipelines.
* **Configuration Drift Mitigation:** Enables platform engineers to version-control and deploy SPL2 data transformation pipelines directly through enterprise CI/CD workflows.

#### B. Cloud-Aligned Configuration Change Tracking (On-Premises)
* Extends configuration change auditing across supported on-prem Web UI and REST API endpoints.
* Automatically records actor identity, execution timestamps, targeted `.conf` files, and operation status (`success` / `failure`) to accelerate troubleshooting and compliance audits.

#### C. Optimized App Management (*Zero/Low Downtime Operations*)
* **Reduced Restarts:** App deletion and uninstall workflows are ~50% less likely to require a full Splunk platform restart.
* **Configuration in `limits.conf`:**
```ini
[reload_on_delete]
disabled = false
```

#### D. Federated Search Validation & Resilience
* Automated capability exchange (*capability handshake*) between federated Search Heads and remote search endpoints.
* Proactively validates supported SPL commands and version compatibility to prevent runtime query failures across distributed hybrid topologies.

---

### 3. ⚠️ Upgrade Considerations & Architecture Guardrails

> [!warning] KV Store Engine Migration (Final Optional Stage)
> * Upgrading to the co-hosted KV Store engine remains optional and can be temporarily deferred in 10.6.x releases.
> * **Migration Notice:** Co-hosted KV Store will become **strictly mandatory** in subsequent major releases (10.7+ and 11.x). Upgrading during the 10.6 transition is strongly recommended.

> [!note] Runtime Environment & Security Baseline
> * **Python 3.13 Runtime:** Continued standardization of the embedded Python environment. Validate custom search commands (CSCs) and legacy Technology Add-ons.
> * **TLS 1.3 Default Encryption:** Enforced modern cryptographic protocols for intra-cluster communication (S2S port 9997 and management port 8089).
