Read Me

The SIEM Log Generator produces realistic security logs — firewalls, Windows, Linux, network devices, cloud proxies — in the exact format each Splunk add-on expects, and ships them to a file, to Splunk over HEC, or to a syslog collector such as SC4S. Use it to feed a lab, test detections, or size an infrastructure.

Simulated data, for testing. The logs this application produces are synthetic. They follow each vendor's documented format and the field extractions of its Splunk add-on, so they parse and map to CIM the way real events would — but they simulate behaviour for testing purposes, and may differ from what a specific device, firmware version or configuration emits in production. Validate detections, dashboards and sizing against real data before relying on them.

Quick start

  1. Create a destination. Configuration → HEC Destinations (or Syslog Destinations), then Test Connection.
  2. Create a sender. Senders → + Add Sender: pick a Technology, tick its Splunk Sourcetypes, set a Frequency and choose the destination.
  3. Start it with the ▶ button. The Logs Generated counter starts climbing.
  4. Check Splunk: index=<your index> earliest=-15m latest=+1h, with no sourcetype filter first.

Destinations

Local File
Appends one event per line to a path on this machine. Useful to inspect the raw format, or to be read by a Splunk Universal Forwarder.
HEC (Splunk)
Sends straight to Splunk's HTTP Event Collector with the sourcetype and source each add-on expects. Configure the URL, port and token once under Configuration → HEC Destinations; each sender can override the index.
Syslog TCP/UDP
Sends to a syslog collector — typically SC4S, which identifies the source and forwards it to Splunk itself. No sourcetype or index is sent: the collector decides.

Delivery format chooses between the two shapes of an event. UF is the event itself, as a forwarder reads it from disk; Syslog adds the priority and header a device sends to a collector. A Local File can hold either, so it offers the choice for every source collected over syslog — defaulting to the shape the source already has. Over HEC the event is always sent as itself, and a Syslog destination offers the choice only where there is one: a source that writes its own priority, or has no forwarder path, is always framed. Windows sources choose Render Format (XML or classic) instead.

Senders

A sender is one continuous stream of events. Three ways to define what it produces:

By Sourcetype
Pick a technology and the sourcetypes you want. Some technologies add their own options — Windows' Render Format (XML or classic), for instance.
By Datamodel
Pick a CIM datamodel; one sender is created for every sourcetype that reaches it. The quickest way to populate Authentication or Network_Traffic from every source at once.
Attack
Runs a finite attack scenario — see Attacks.

Senders are grouped into Active and Inactive; ▶/⏸ starts and stops them, and clicking Name sorts both tables. Editing a running sender restarts it with the new settings.

Environment

By default every source invents its own hostnames, IPs and users, so nothing lines up across sources. Describe your lab once and every sender draws from it:

  • Configuration → Assets & Identities: assets (endpoints, servers, domain controllers, firewalls, routers…) with their IP, hostname and FQDN, and identities optionally linked to an asset.
  • Configuration → Network Pools: IP ranges for the source and destination ends of network traffic.

Then tick Use Environment on a sender. The slider mixes your environment with random defaults — 100% means every event is about one of your entities. Within an event, a machine's hostname, IP and linked account always stay together, so correlations work across sources.

Attacks

An attack emits a set Number of Events over a Duration, in the format of its source, then stops and shows Done under its name. Run it against a normal sender on the same source: the baseline is the noise, the attack is what a detection should pick out of it. Any field marked fixed can be pinned — the targeted user, the attacker IP. The Catalog lists every attack with the datamodel it lands in and a link to the matching Splunk detection.

A few detections need more than the events: one may end in a lookup against Enterprise Security's own identity list, and stays silent until that list holds what the attack sends. No generator can write those identities, so the attack shows a warning above its configuration with the steps and the exact value to copy — add that one row once and every run after it matches.

An attack that several products record — a port scan seen by Palo Alto, FortiGate and Cisco ASA — lets you untick the sourcetypes you don't run. The count you ask for is the count sent: the events are shared evenly between the sourcetypes ticked, each probe recorded by one device, so the detection still sees the whole scan. Such an attack goes to HEC or a Local File, never syslog, where one stream would carry every sourcetype under one; a file receives the events exactly as HEC sends them.

Simulation

A simulation reproduces a daily volume rather than a rate: give it a duration and a volume per source (GB, MB or KB), and it computes the rate from the measured size of each source's events. Over HEC, set a default index and override it per source. The countdown replaces the running status and the simulation stops itself at zero.

Troubleshooting

The counter climbs but nothing shows in Splunk
HEC answering 200 means queued, not indexed. Most often the events are there but in the future: when Splunk's clock is behind this machine's, every relative search ending at now misses them. Search with latest=+1d, and sync both clocks with NTP.
A syslog source isn't recognised by SC4S
Look at sourcetype=sc4s:fallback. An event there with PRI=13 arrived with no syslog priority at all — check the sender's Delivery format. Nothing at all? Check the collector is receiving: syslog-ng-ctl stats inside the container.
